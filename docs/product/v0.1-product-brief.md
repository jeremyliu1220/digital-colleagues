# Digital Colleagues v0.1 Product Brief

## Product statement

Digital Colleagues is an open-source, local-first control plane and reference stack for
building persistent AI coworkers. It makes a coworker's durable identity, delegated
authority, responsibilities, finite work, wake cycles, proposed effects, human approval,
and audit trail visible and testable.

The working tagline is **Build, govern, and run persistent AI coworkers.**

## The distinction that matters

| System | Primary interaction | Durable mandate | Owns ongoing work | Governed effects | Persistent audit causality |
| --- | --- | --- | --- | --- | --- |
| Assistant | Responds to a request | Usually absent | No | Limited | Usually session-scoped |
| Task agent | Executes a bounded goal | Temporary | Sometimes | Tool-specific | Run-scoped |
| Digital colleague | Operates under a named, revisable mandate | Required | Yes | Explicit proposal and approval boundaries | Required across restarts |

A digital colleague is not defined by autonomous tool use. It is defined by persistent
identity, delegated and bounded authority, durable responsibility, resumable work,
governed effects, and inspectable causality.

## Intended audiences

- Developers and platform teams building local or self-hosted agent systems.
- Enterprise architects evaluating the primitives needed before pilot deployment.
- Security, governance, and audit practitioners reviewing authority and effect boundaries.
- Technical teams who want a deterministic reference path before adding real providers.
- Contributors researching persistent-agent architecture.

## Golden Path

The v0.1 Golden Path is a five-minute local demonstration:

1. Clone the future public repository and start the documented Docker Compose topology.
2. Open Studio on its loopback address and exchange the one-time bootstrap token.
3. Create a draft colleague with name, role, whom it serves, mission, timezone, working
   hours, working style, scope, capabilities, and responsibilities.
4. Review the generated identity card and authority diff. An Admin confirms the exact
   draft revision.
5. Assign a finite piece of work, restart the stack, and observe that identity, mandate,
   work, and causal history persist.
6. Trigger a deterministic wake cycle. The colleague proposes a fully specified effect.
7. An authorized human approves or rejects that exact effect. A replay or stale approval
   is refused.
8. The reference channel produces an ActionResult, and Studio shows the causal chain from
   input event through agenda, decision, approval, effect, and result.

No network provider or real-world side effect is required for the reference path.

## v0.1 outcome

The release should let a reviewer answer, with inspectable records:

- Who is this colleague and which tenant namespace owns it?
- What may it do, what must it do, and which revision granted that authority?
- What work survives process restart?
- Why did it wake and how was the next agenda chosen?
- Which exact effect was proposed, who could approve it, and what result followed?
- Can a model or service identity impersonate a human approver? The answer must be no.

## Maturity boundary

v0.1 targets a **local reference implementation and architecture evaluation**, not an
enterprise deployment.

| Claim | v0.1 position |
| --- | --- |
| Local deterministic reference path | In scope after its milestone gate passes |
| Explicit identity, authority, approval, and audit primitives | In scope |
| Local multi-user role demonstration | In scope with local authentication limits |
| Enterprise architecture starter | Only as documented boundaries and extension ports |
| Real-provider pilot readiness | Not claimed |
| PostgreSQL, distributed execution, or high availability | Not claimed |
| Production tenancy isolation | Not claimed |
| Enterprise IAM or lifecycle management | Not claimed; OIDC, SSO, and SCIM are gaps |
| Security, privacy, or regulatory compliance | Not claimed |
| Production readiness | Not claimed |

The parent research system has useful local and offline evidence, but incomplete human
evaluation and live-provider acceptance cannot be promoted into public release claims.

## P0 boundary

P0 establishes only plans, provenance, licensing intent, a public-data boundary, and tests
for those records. Passing P0 means the planning and public-boundary gate passed. It does
not mean the product exists, the design is secure, or any production property is proven.
