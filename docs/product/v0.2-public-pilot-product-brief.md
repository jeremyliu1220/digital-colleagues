# Digital Colleagues v0.2 Public Pilot Product Brief

Status: P12 Public Pilot Continuity Rebaseline. This document defines future Public Pilot
contracts; P12 implements governance only. The executable product remains the accepted
P11R baseline and no P13-P20 capability is implemented.

## Product statement

Digital Colleagues v0.2 is planned as a local-first Public Pilot for deploying and
governing persistent AI coworkers that interact through familiar work applications while
keeping identity, authority, resources, effects, persistence, and audit causality explicit.
It is a pilot, not production-ready 1.0.

## Intended pilot outcome

A successful pilot lets an Admin and reviewer answer, from durable records:

- Which exact non-executable AgentPackage version and digest defined this colleague?
- Which namespaced ColleagueDeployment, Profile, Mandate, and Policy are current?
- Which ExternalConnection authenticates the Agent, and which resources/actions does its
  current ConnectorGrant permit?
- Which source reference and data version caused a semantic decision and exact effect?
- Did a human authorize the exact effect, or did a distinct
  AutomaticEffectAuthorization prove the fixed low-risk boundary?
- What was attempted, what result was observed, and how did reconciliation finish?
- Can package content, a model, a connector, or another Agent grant itself authority? The
  answer must be no.

The planned operating targets are:

- start Studio within five minutes on a Mac that already has Docker Desktop and a
  downloaded release;
- deploy the first interactive Agent within fifteen minutes when an OpenAI key, Entra App
  ID, and dedicated Microsoft 365 Agent account are already available;
- run no more than ten active Agents on one execution host;
- support a Mac local profile and a Linux/Mac mini always-on Docker profile; and
- make it explicit that a purely local Agent stops when its MacBook sleeps or powers off.

These targets require later measurement. P9 supplies no runtime or live evidence.

Studio is the Admin control plane. Managers and colleagues primarily interact with an
Agent through Outlook, Teams, and Planner; SharePoint contributes selected read-only source
context.

## Product objects and authority

| Object | Product meaning | Authority rule |
| --- | --- | --- |
| AgentPackage | Non-executable, versioned, digest-bound declarative blueprint containing schema-valid metadata, localized display text, prompt, bounded workflow declaration, and requested capabilities | Requests only; never installs, activates, self-grants, or expands authority |
| ColleagueDeployment | Namespaced instance created from one exact package version/digest, with its own Profile, Mandate, Policy, lifecycle, and external bindings | Admin-reviewed exact bindings determine authority; package content does not |
| ExternalConnection | Managed credential connection for one provider/application/account | Authentication only; grants no resource or action |
| ConnectorGrant | Admin-created, revisioned, resource/action-specific binding from a connection into the current Mandate and Policy | All resource use and effects must match it exactly |
| AutomaticEffectAuthorization | Durable authorization produced only after proving an exact low-risk policy, Mandate, Policy, ConnectorGrant, source/data version, and budget | Separate from HumanApprovalDecision and never authored by MODEL/SERVICE as a human decision |
| SourceReference / SourceCursor | Safe external-source locator/version and restart cursor | Not a body store, Semantic Memory, permission, or authority source |

Provider output, package content, localized prompts, external content, and UI state are
untrusted data. The server reconstructs authoritative fields and fails closed on unknown,
missing, stale, revoked, cross-namespace, cross-Agent, digest/schema mismatch, unbound
resource, ambiguous authority, or budget overflow.

## Package safety and lifecycle

An AgentPackage is not an S4 Skill. P12-P20 do not add executable Skills, Skill Learning, or
an arbitrary plugin system. A package cannot include or trigger Python, Node, shell,
binary, browser automation, plugin code, dynamic import, `eval`, `exec`, or unbounded
loops.

Allowed sources are official built-ins, local development packages, and GitHub Release
artifacts with a valid GitHub artifact attestation. Attestation binds artifact digest to
source/build identity; it does not establish safety. Before install, Studio must show
signer, repository, workflow, digest, requested capabilities, permission diff, and the
Admin's trust decision. Install remains inert until a reviewed deployment draft binds
current authority. Upgrade creates a new draft and never auto-applies. Rollback selects an
accepted and still-trusted exact version; stale or revoked versions are refused.

## Deferred-capability boundaries

- External Outlook, Teams, Planner, and SharePoint bodies are bounded, temporary context
  for the current evaluation. They do not create S1 Semantic Memory, embeddings,
  long-term synthesized facts, or a learning loop.
- Multiple deployments on one host are lifecycle isolation, not S3 shared knowledge,
  delegation, Agent-to-Agent messaging, collaboration, or shared memory.
- Each deployment isolates namespace, work, credentials, connections, grants, budgets,
  effects, and audit. Cross-Agent access and Agent loops are denied by default.
- AgentPackage remains a declarative product configuration and is not S4 Skill execution.

## OpenAI contract planned for P13

The first provider is the OpenAI API and the fixed initial candidate is `gpt-5.5`.
After its parser-first gate, P13 uses the Responses API, Structured Outputs, and explicit
`store:false`. OpenAI receives
no function tools, hosted tools, MCP, browser/computer use, shell, connector credentials,
or direct execution authority. The model emits only a bounded schema-valid semantic
decision; the server reconstructs identifiers, principals, namespace, time, authority,
source versions, and exact effect fields.

The gateway must bound input/output, usage and cost, timeouts and retries, and handle
refusal, incomplete output, schema errors, prompt layering, prompt injection, and model
provenance. The model cannot change a Mandate, Policy, ExternalConnection, ConnectorGrant,
human role, or approval. Official docs and actual project access are rechecked at P13 start
and before each live acceptance. Incompatibility requires a Change Decision; no silent
model substitution is permitted.

## Microsoft 365 contract planned for P14

Each Agent uses one dedicated Microsoft 365 work/school account through delegated OAuth
device-code public-client authentication. The pilot supports a project-operated verified
multi-tenant public client App and an enterprise-supplied single-tenant public client App
ID. Ordinary user consent, Admin pre-consent, and selected-resource configuration are
separate durable lifecycle facts.

- Outlook maintains a SourceCursor for each allowed mail folder's delta stream.
- Teams exposes no public webhook or cloud relay. It polls only Admin-allowlisted chats
  over a bounded date window and deduplicates message ID plus etag.
- Planner is read/write. Every update supplies the latest ETag with `If-Match`; stale ETag,
  409, or 412 causes reread and reevaluation and never overwrite.
- SharePoint is read-only within selected sites/folders. Unbound or out-of-selection
  resources are refused.
- Later gates cover Graph 401/403/429/5xx, refresh and revocation, throttling, ambiguous
  sends, retry, reconciliation, and restart cursors.

P14 owns bounded explicit synchronization, provider dedupe, Outlook existing-thread reply,
Teams allowlisted existing-chat reply, and Planner latest-ETag `If-Match` transports. Every
P14 write uses an existing exact current HumanApprovalDecision. SharePoint remains selected-
resource read-only. Mock, stub, or loopback results never establish named Microsoft 365
compatibility.

## Continuation, memory, trigger, and recovery

P15 adds ProjectScope containing only deployment Namespace and `project_id`, the exact
five-value ProjectContinuationState, exact WaitingConditions, HUMAN-accepted GoalBinding,
mandatory checkpoints, and new-process empty-chat recovery. P15 accepts only an explicit
normalized signal bound to one exact wait and never correlates a raw provider event.

P16 adds tiered semantic-memory admission. MemoryAdmissionDecision is only `admit` or
`reject`; correction, supersession, revocation, deletion, and expiry are separate immutable
post-admission lifecycle. Retrieval is bounded and checkpointed by canonical set ID/digest,
never copied memory body or authority.

P17 adds recurring schedules, heartbeat, autonomous polling, raw-event correlation,
ambiguity quarantine, wake, and startup recovery. DST gaps skip, folds use the earlier
occurrence, and catch-up emits at most the latest occurrence within 24 hours.
RecoveryScanCheckpoint is an optimization; durable incomplete state is authoritative.

## Effect policy and ownership

An effect is `auto_within_boundary` only when it is provably one of:

- a routine reply in an existing internal email thread or existing allowlisted Teams chat,
  with identical original participants, same tenant, no attachment, and no new mention;
  or
- a Planner action whose plan, task, fields, assignee, ETag/data version, Mandate, Policy,
  ConnectorGrant, and budget match exactly.

An effect is `require_approval` for a new recipient, new chat, external domain, attachment,
new mention, cross-tenant message, or ambiguous authority/binding/version/risk. It is
`deny` or fail closed outside Mandate/Policy/ConnectorGrant; on stale data, ETag, or
revision; on revoked/expired connection; over budget/rate limit; across Agent or tenant;
on capability self-grant; or whenever the automatic boundary cannot be proven.

AutomaticEffectAuthorization and HumanApprovalDecision remain separate durable types,
authoring rules, and audit semantics. MODEL and SERVICE never author a
HumanApprovalDecision. P18 alone creates AutomaticEffectAuthorization and reuses the P14
transports, outbox, idempotency, ActionResult, and reconciliation. It does not add a
connector write adapter. The P19 built-in project tracker composes only accepted P13-P18
primitives, does not request `delete_task` by default, and fails if a required transport is
absent. Later gates prevent self-reply, Agent loops, duplicates, replay, and notification
flooding.

## Privacy, secret, and language contracts

Mac live mode checks FileVault. Secret directories are mode `0700`; credential files are
mode `0600`; only necessary services receive them through read-only file mounts. Keys and
tokens never enter environment variables, SQLite, audit, backup, diagnostics, logs,
errors, command arguments, or public evidence. Always-on Linux uses an operator-provided
encrypted volume; unproved storage encryption keeps live readiness `not_evaluated` or
blocks live mode.

Public files contain no real accounts, tenants, endpoints, external bodies, provider
receipts, live acceptance, personal data, or credentials. Persistent connector state is
limited by default to SourceReference, etag, digest, cursor, safe projection, and causal
record. Temporary body processing is bounded, redactable, discarded on schedule, and
cleaned after crashes as specified in the v0.2 privacy boundary.

Studio, quickstart, Catalog, wizard, and official built-in Agent content first support
`zh-TW` and `en-US`. P9 defines the i18n contract; P10 creates translation keys. Localized
metadata and prompts never alter schema, capabilities, authority, permissions, or safety
defaults. Missing translation fails safe.

## Public Pilot success and evidence

P12-P19 may establish only `static`, `synthetic_offline`, or explicitly labeled `loopback`
results. OpenAI and Microsoft 365 live availability remain `not_evaluated` without actual
private access. P20 requires two Microsoft 365 test tenants, ten dedicated Agent test
accounts, one usable OpenAI test project, one verified project multi-tenant Entra public-
client App, one BYO single-tenant App, delegated user- and Admin-consent testing, real
Outlook/Teams/Planner/SharePoint test data, and private live-evidence storage outside the
public tree. Its live gate cannot be replaced by mock, stub, or loopback results.

A v0.2 Public Pilot release can be considered only after P12-P20 each complete independent
acceptance, correction if needed, final acceptance, fast-forward merge, and main
verification, followed by separate user authorization for tag/push/publish/upload/Release.

enterprise IAM, production tenancy, large multi-tenancy, compliance certification,
